Vertical Agents Survey

Harness 论文 Poster 合集

共 11 篇。每篇都按同一结构整理：研究问题 → 核心机制 → 主证据 → 真正支持什么 → 证据边界 → 为什么对 Harness 重要。 内容严格来自已经完成 primary-source verification 的 Structured Paper Notes；没有把 MCP、LangGraph、E2B 等官方文档伪装成论文。

01
Action Interface

SWE-agent

接口不是透明 plumbing：底层模型固定时，ACI 的动作、反馈与上下文设计本身就能改变测得的 Agent 能力。
02
State & Memory

MemGPT

Context ≠ Memory：长期信息要先存在模型外，再通过检索、移动和压缩机制回到 model-visible context 才能影响推理。
03
Durable State

LongHorizon-Harness

长程任务不只是“塞更多 context”：把经核验的进展外化成持久 task state，并让 fresh executor 基于它继续工作，可以显著改变系统表现。
04
State-based Verifier

AppWorld

好的 verifier 可以检查最终状态而不是死匹配轨迹：允许多条合法路径，同时拒绝未授权的 collateral state changes。
05
Policy-rich Verification

τ-bench

Terminal state 正确不等于过程合规：reward=1 仍可能漏掉没有被 verifier 编码进去的 policy violation。
06
Reproduction & Judge

PaperBench

强验证往往是组合式的：fresh reproduction 检查 artifact 可执行性，层级 rubric 检查完成度，LLM judge 负责规模化评分，但 judge 本身也要被评估。
07
Verifier Integrity

SpecBench

把 visible tests 做满不等于满足 specification；held-out compositional tests 能直接暴露 verifier coverage gap 与 proxy gaming。
08
Adversarial Audit

BenchJack

Verifier 本身也是攻击面：隐藏测试、规则评分或 LLM judge 都可能被利用，因此 benchmark 需要 adversarial audit，而不只是“再多藏几个 test”。
09
Training Harness

Polar

训练阶段的 Harness 还要解决 token-faithful trajectory、异步 rollout 与吞吐问题；这些系统机制能显著改变 RL 训练效率。
10
Training-Agent Disaggregation

Agent Lightning

Agent 执行与 RL trainer 可以解耦：runtime 继续跑原有 agent，trainer 通过统一 trajectory / reward 数据接口接入学习。
11
Verifier Decomposition

APIGen

格式正确、执行成功、语义对齐是三个不同 verification object；任何一个成立都不能自动推出另外两个。
阅读建议：如果是准备组会 / 答辩式提问，优先看 SWE-agent、MemGPT、LongHorizon-Harness、AppWorld、τ-bench、PaperBench、SpecBench、BenchJack； Polar 与 Agent Lightning 主要支撑 training/runtime lifecycle，APIGen 主要支撑 verifier decomposition。

SWE-agent

SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering
Yang et al. · 2024; arXiv:2405.15793v3 · 重要性：Anchor
Contract & Action SurfaceState & ContextHarness Effects / Comparability

1 · 研究问题

SWE-agent 研究的是：LM agent 在解决软件工程任务时，应该怎样与计算机交互。论文把接口本身而不只是底层模型视为重要设计变量，因为动作原语以及环境返回给模型的反馈，决定了模型究竟能可靠地看到什么、做什么。

2 · 核心方法 / 系统机制

作者定义 Agent-Computer Interface (ACI)，即 LM agent 与计算机之间的抽象层。ACI 不只是 tool signature，还包括可用命令 / 动作、observation 与 feedback 格式、搜索 / 导航、文件查看 / 编辑、lint / error feedback、context/history 处理，以及让 LM 更容易操作计算机的 guardrails。

3 · 一眼看懂的主证据

11.0%
Shell-only
→
18.0%
SWE-agent ACI
+7.0 pp Resolved · SWE-bench Lite · GPT-4 Turbo
实验 / 证据条件以原论文与核验笔记为准。

4 · 关键证据

  1. §1 Introduction；Figure 1 及附近正文。 ACI 同时由 agent 可用的命令和计算机返回的反馈格式定义，直接说明它比 function signature 更宽。
  2. §2 Agent-Computer Interfaces；§3 The SWE-agent ACI；Figure 2；§4 前的 context-management 讨论。 ACI 打包了小型 action set、command docs、file search/navigation、editor/viewer、lint/error feedback、observation formatting、context compression 和 guardrails。
  3. §4 Experimental Setup；§5 Results；Table 1；Table 3。 在 SWE-bench Lite（300 tasks）、固定 GPT-4 Turbo gpt-4-1106-preview、每实例预算 $4 条件下，SWE-agent 为 18.0% Resolved，Shell-only GPT-4 baseline 为 11.0%。
  4. §5.1 / Table 3 ACI ablations。 同一 benchmark/model 设置下：editor+lint 18.0，无 lint 15.0，无 edit action 10.3；summarized search 18.0，iterative search 12.0，无 search 15.7；100-line viewer 18.0，30-line 14.3，full file 12.7；last-five observations 18.0，full history 15.0；去掉 demonstration 后 16.3。

5 · 这篇论文真正支持什么

  • Literature-supported面向 LM 的 action interface 同时包含 action affordance 与 observation/feedback design。
  • Literature-supported底层模型固定时，接口设计可以实质性改变 benchmark performance。
  • Literature-supportededitor、search、viewer、feedback、context choice 在该实验中都有实证影响。
  • QualifiedSWE-agent 强力支持“interface design 是 capability elicitation variable”，但 +7pp 是一个 bundled ACI intervention，不是 schema-only causal effect。

6 · 证据边界：不要过度解读

  • 不建立 ACI 是领域通用的 Harness 标准定义。
  • 不证明 JSON/tool schema 单独导致 18.0% vs 11.0%。
  • 不能把 SWE-agent 的全部 gain 都记为 contract-layer gain；同时改变了 observation、editor/search、demonstration、history/context 与 guardrails。
  • 不建立 ACI 自带 authorization、sandbox、durable state 或 task-success verification。

7 · 为什么它对 Harness 综述重要

接口不是透明 plumbing：底层模型固定时，ACI 的动作、反馈与上下文设计本身就能改变测得的 Agent 能力。

MemGPT

MemGPT: Towards LLMs as Operating Systems
Packer et al. · 2023; arXiv:2310.08560 · 重要性：Anchor
State & ContextExecution Runtime & Recovery（边界证据）Harness Effects / Comparability

1 · 研究问题

MemGPT 解决 long-running / multi-session interaction 中有限 context window 的问题。它最重要的系统思想，是把较小的 model-visible working context 与更大的 external memory 区分开，并提供跨这些层移动、检索、总结和编辑信息的 agent/runtime 机制。

2 · 核心方法 / 系统机制

系统使用模型能直接看到的 main context，以及 recall / archival memory 等 external store。queue manager 处理 context pressure、eviction 和 summarization；function executor 暴露 memory-management operations，让模型在需要时检索或更新外部 memory。

3 · 一眼看懂的主证据

32.1%
GPT-4 baseline DMR
→
92.5%
GPT-4 + MemGPT
Deep Memory Retrieval · Multi-Session Chat
实验 / 证据条件以原论文与核验笔记为准。

4 · 关键证据

  1. §2 MemGPT；§2.1 Main Context；Figure 3。 main context 是 model-visible；recall/archival 信息在外部，必须被 retrieve 回 main context 才能影响 inference。
  2. §2.2 Queue Manager；§2.3 Function Executor；Figure 3。 系统管理 FIFO-like context、recall storage、memory-pressure warning、eviction、recursive summary 以及显式的数据移动 / 检索。
  3. §3.1.1 Deep Memory Retrieval；Table 2。 Multi-Session Chat 中，五个历史 session 后进行第六 session QA。DMR accuracy：GPT-3.5 Turbo 38.7→66.9%，GPT-4 32.1→92.5%，GPT-4 Turbo 35.3→93.4%。核验模型包括 gpt-4-0613、gpt-4-1106-preview、gpt-3.5-turbo-1106；评测用 ROUGE-L + LLM judge。
  4. §3.2；Figures 5 and 7。 效果并不在所有 base model 上一致；较弱的 function-calling 能力会限制 memory-control design。

5 · 这篇论文真正支持什么

  • Literature-supportedmodel-visible context 与 external long-term memory 是不同存储 / 访问对象。
  • Literature-supportedruntime 可以通过显式 memory movement、retrieval、eviction、summarization 管理 context pressure。
  • Literature-supported在论文 multi-session setting 中，external-memory access 可以显著改善 deep retrieval。
  • QualifiedMemGPT 展示了重要的 state/context runtime pattern，但“何时、检索 / 存什么”部分由模型自己决定，不是纯 runtime policy。

6 · 证据边界：不要过度解读

  • 不建立类似 graph checkpoint 的 durable workflow checkpoint/resume abstraction。
  • 不证明 crash recovery、exactly-once execution、transaction rollback 或 external side-effect compensation。
  • 它的 interrupt/control-flow 不能拿来证明 persistent execution recovery。
  • 不证明所有 base model 同样获益；function-calling competence 是重要条件。

7 · 为什么它对 Harness 综述重要

Context ≠ Memory：长期信息要先存在模型外，再通过检索、移动和压缩机制回到 model-visible context 才能影响推理。

LongHorizon-Harness

LongHorizon-Harness: Advancing Long-Horizon Agents for Real-World Tasks
Ma et al. · 2026-08-03; arXiv:2608.01964v1 · 重要性：Anchor
State & ContextExecution Runtime & RecoveryVerification & RewardHarness Effects / Comparability

1 · 研究问题

LongHorizon-Harness 处理长时 Agent 的两个问题：有效进度容易被越来越长的 interaction history 淹没，后续步骤还可能基于未核验的假设继续执行。它把 task progress 外部化成 persistent structured state，并把执行与独立 environment auditing 角色分开。

2 · 核心方法 / 系统机制

设计在单一不断增长的 model context 之外维护 explicit task state。fresh-context executor 执行 subtasks；manager 推进任务；auditor 独立检查 environment，只有经过验证的事实才能写进 persistent task record。

3 · 一眼看懂的主证据

51.8%
WeaveBench baseline
→
80.7%
LongHorizon-Harness
Qwen 3.7-Plus · full Harness intervention
实验 / 证据条件以原论文与核验笔记为准。

4 · 关键证据

  1. §2.1 Overview；§2.2 Task-state update；Figure 2。 架构区分 task state S_i、environment state e_i 和 raw executor trajectory。executor 可以每轮使用 fresh context，而 persistent task record 保留 verified progress。
  2. §2.2 Task-state update；§2.4 Auditor / Independent environment inspection / Read-only authority。 auditor 独立检查 environment，并拥有 read-only authority；只有 clean evidence 才进入 persistent task state。
  3. §3.1 Experimental Setup；§3.2；Tables 1–2；Figure 3。 primary backbone 为 Qwen 3.7-Plus，默认 manager/executor/auditor 同 backbone。结果包括 WeaveBench 51.8→80.7%、Terminal-Bench 2.1 69.7→77.2%、OSWorld 2.0 2.8→8.3%。条件：executor timeout 1800s，manager/auditor 300s，最多 25 MEA rounds；WeaveBench 114 tasks，OSWorld 108 tasks；Terminal-Bench 每 task 3 次独立运行取平均。
  4. §3.4 Recovering from a stalled interaction；Figures 7 and 10。 Qwen 3.7-Plus paired case study：Wireshark 0.59→0.92，Lighthouse 0.53→0.85，展示通过保留 verified progress 从 stalled/repetitive interaction 恢复。

5 · 这篇论文真正支持什么

  • Literature-supportedexplicit model-external task state 可以跨 fresh execution context 保存 verified progress。
  • Literature-supported架构把 executor 与独立、read-only environment auditor 分离。
  • Literature-supportedbase model 固定时，完整 LongHorizon-Harness intervention 在多个 long-horizon benchmark 上有显著提升。
  • Qualified这是“state architecture + harness organization 能影响 system capability”的强证据，但 gain 属于完整 intervention。

6 · 证据边界：不要过度解读

  • 不证明 state store 单独造成全部提升。
  • 干预同时包含 explicit state、manager/executor/auditor、fresh contexts、verification、multiple rounds 与不同 inference/control budget。
  • 两个 recovery example 是 case study，不是 population-level causal estimate。
  • Claude Opus OSWorld subset 在摘要与 Table 3 有内部数值不一致；最终引用应优先 table，并记录 discrepancy。

7 · 为什么它对 Harness 综述重要

长程任务不只是“塞更多 context”：把经核验的进展外化成持久 task state，并让 fresh executor 基于它继续工作，可以显著改变系统表现。

AppWorld

AppWorld: A Controllable World of Apps and People for Benchmarking Interactive Coding Agents
Trivedi et al. · 2024; arXiv:2407.18901 · 重要性：Anchor
Verification & RewardState & ContextHarness Effects / Comparability（说明 score 到底代表什么）

1 · 研究问题

AppWorld 希望在可控 simulated environment 中评估跨多个应用的 interactive agent，使 success 可以通过程序方式检查，而不只依赖 action log 或 reference trajectory。核心难点是既接受多种有效路径，又检测意外 state change。

2 · 核心方法 / 系统机制

Evaluator 从 initial state 计算 DB state diff，并检查人工定义的 expected 与 allowed change set。所有 expected change 必须发生，expected+allowed 之外的变化会失败，因此能显式检测 collateral damage。

3 · 一眼看懂的主证据

750
tasks
→
457
APIs
250 scenarios · 9 simulated apps
实验 / 证据条件以原论文与核验笔记为准。

4 · 关键证据

  1. §1 “Programmatic and Robust Evaluation Suite”；§3.2 Evaluation；Figure 3。 用 expected changes C_i^{expect} 和 optional allowed changes C_i^{allow} 比较 final DB 与 start state；programmatic assertions 要求所有 expected change，并拒绝未批准的 delta。
  2. §3.2 Evaluation。 作者明确把 state-based evaluation 与 process/path matching 对比，允许多种 action sequence 到达同一合法 final state。
  3. 实验设置。 750 tasks / 250 scenarios，9 个 simulated daily apps，457 APIs。TGC 是单 task 全部 tests pass；SGC 要求 scenario 中全部 task pass。

5 · 这篇论文真正支持什么

  • Literature-supportedfinal-state/state-diff verification 与“API 成功执行”不同。
  • Literature-supportedstate predicate 可以接受多种合法路径，同时检测指定 collateral DB change。
  • QualifiedAppWorld 是 simulated app world 中 encoded outcome correctness 的强例子。

6 · 证据边界：不要过度解读

  • AppWorld pass 不证明过程本身合规。
  • 未编码的 policy、authorization、timing、legal 或 external side-effect 条件可能完全不可见。
  • simulated/fictitious environment 不建立真实生产 business validity、authentication 或 regulatory correctness。

7 · 为什么它对 Harness 综述重要

好的 verifier 可以检查最终状态而不是死匹配轨迹：允许多条合法路径，同时拒绝未授权的 collateral state changes。

τ-bench

τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains
Yao et al. · 2024; arXiv:2406.12045 · 重要性：Anchor
Verification & RewardState & ContextHarness Effects / Comparability

1 · 研究问题

τ-bench 在多轮客服交互中评估 tool-using agent，包含 user simulator、domain policy、API 和可变 DB state。它特别适合说明：terminal-state reward 很有价值，但在 policy-rich workflow 中也有明显边界。

2 · 核心方法 / 系统机制

每个 task 有 hidden user instruction、ground-truth DB writes，以及可选 required output strings。Reward 将 action/state component（final DB 必须等于唯一 annotated outcome）与 output-information component 相乘；重复试验使用 pass^k 总结。

3 · 一眼看懂的主证据

r_action
final DB outcome
→
r_output
required user info
r = r_action × r_output · pass^k measures repeated-run reliability
实验 / 证据条件以原论文与核验笔记为准。

4 · 关键证据

  1. §3 Reward；Figure 2。 r=r_{action}\times r_{output}。r_{action} 要求 final DB 等于唯一 target outcome；r_{output} 检查必须告诉用户的信息。
  2. §3 reward 定义后紧接的讨论。 作者明确写 reward=1 可能只是“necessary but not sufficient”；例如没有取得用户明确确认就执行退货，会违反 policy，但仍可能满足 terminal reward。
  3. §3 Domain policy。 一部分 restriction 由 API check 强制；另一部分需要 agent 自己遵守，并没有机械强制。
  4. §3 Pass^k metric。 pass^k 估计在 stochastic agent/user messages 下，k 个 iid trial 全部成功的概率；它测的是同一 reward 定义下的 repeated-run reliability，不是 reward validity。

5 · 这篇论文真正支持什么

  • Literature-supportedtool execution success 与 terminal DB correctness 是不同 verification object。
  • Literature-supportedterminal DB+output reward 可以客观度量指定 outcome。
  • Literature-supportedcorrect terminal state 不必然建立 process/policy compliance。
  • Literature-supportedpass^k 衡量 repeated stochastic trials 的可靠性。

6 · 证据边界：不要过度解读

  • reward=1 不证明所有 domain policy 都被遵守。
  • API 不机械强制所有 policy。
  • pass^k 不会让不完整 verifier 变完整。
  • 不应把后续 τ-family 新增的 communication/policy assertion 机制倒灌到 original τ-bench，除非另行核验。

7 · 为什么它对 Harness 综述重要

Terminal state 正确不等于过程合规：reward=1 仍可能漏掉没有被 verifier 编码进去的 policy violation。

PaperBench

PaperBench: Evaluating AI's Ability to Replicate AI Research
Starace et al. · 2025; arXiv:2504.01848 · 重要性：Anchor
Verification & RewardObservability / Provenance / ReplayEvaluation / Training / Deployment lifecycle

1 · 研究问题

PaperBench 面向 long、open-ended research replication task，这类任务既不能靠简单 unit test，也很难用单个 scalar metric 完整衡量。它把“artifact 是否真的能重现结果”与“科学复现 rubric 完成了多少”分开，并且单独评估用于规模化 grading 的 model judge。

2 · 核心方法 / 系统机制

评测包含 fresh reproduction、large expert-authored hierarchical rubric，以及基于 LLM 的 rubric grader。JudgeEval 用 human-graded leaf 来评估 judge 本身。

3 · 一眼看懂的主证据

8,316
rubric leaf nodes
→
≈$66
auto-judge / paper
20 ICML 2024 papers · fresh Ubuntu 24.04 + A10 reproduction
实验 / 证据条件以原论文与核验笔记为准。

4 · 关键证据

  1. §2.2 Reproduction；Figure 1。 Agent run 结束后，submission 被复制到新的 Ubuntu 24.04 VM + A10 GPU，执行 reproduce.sh。报告实验中 reproduction script 最多 12 小时；agent-generated script 平均 5.5 分钟。只有在 fresh environment 中重新生成的结果才算 replicated。
  2. §2.3 Grading；Figure 2；§3.1 rubric design。 rubric 是 weighted tree，leaf 为 binary criteria。20 篇 ICML 2024 Spotlight/Oral papers 共 8,316 leaf nodes，并与原论文作者共同制定。
  3. §2.4 Requirement Types。 leaf 分成 Code Development / Execution / Result Match，因此能给 partial progress，而不是只看一个 terminal bit。
  4. §4；§4.1 SimpleJudge；§4.2 JudgeEval；Table 3；Appendix G。 人工 grading 每篇要几十小时，所以 SimpleJudge 自动逐 leaf 评分。主设置用 o3-mini-high；自动 judge 约 $66/paper。JudgeEval 用 human-graded partial replications，主 judge macro F1 约 0.83。

5 · 这篇论文真正支持什么

  • Literature-supported在独立 fresh environment 中重新执行，能验证 submitted artifact 是否真的可以 regenerate claimed output。
  • Literature-supportedhierarchical rubric 让 open-ended replication 可分解并支持 partial-progress scoring。
  • Literature-supportedPaperBench 明确区分 implementation、execution、result-match evidence。
  • Literature-supportedLLM judge 可以让超大 expert rubric 在操作上可扩展。

6 · 证据边界：不要过度解读

  • fresh reproduction 不证明所有 semantic/scientific criteria 都满足。
  • hierarchical rubric 不保证 rubric 完整或绝对正确。
