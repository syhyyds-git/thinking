0这套系统到底在解决什么问题

核心不是“让模型批量写题”，而是同时压住模型幻觉，并把题目从固定模板扩展成有证据、有变化的任务空间。

问题一：模型幻觉——答案看起来合理，但没有可靠来源

最容易看见的是数字幻觉，例如模型凭印象写出“美国 2010 年某州人口比例”。但 Source 要约束的不只是数字，还包括定义、规则、适用范围、例外、方法、时间口径和跨文档关系。任何会改变答案的关键主张，都应该能回到模型实际看见的原文。

因此 Source 既是证据边界，也是任务边界：它不仅证明答案对不对，还决定这份材料究竟支持比较、计算、规则应用、决策还是只支持摘要。

问题二：固定模板——题目数量增加了，任务空间却没有扩大

如果所有题都套“先做 A、再做 B”的固定文本模板，表面上有很多题，实际只是在换名词。模型学到的是模板复读，而不是面对不同材料时选择操作、补齐条件、组合证据和改变交付物。

系统因此把 Seed（怎么完成一类任务） 与 TaskSignature（这一次具体出了什么题） 分开。Seed 提供可复用工作流；Source Card 和 Source Package 提供不同事实形状；Selector、stable/mutated/source-native 三种生成角色以及多文档操作共同扩展任务多样性。

内容空间

医学、政府、法律和财经 Source 带来不同实体、规则、数值、时间和证据形状。

操作空间

题目可以计算、比较、判断、应用规则、制定计划或综合多份材料，而不是统一做摘要。

结构空间

可以是单文档、多文档、stable、mutated、source-native，也可以真正触发 conditional work 或历史轮次。

交付物空间

答案可以是比较表、计算过程、决策路径、风险计划或证据综合；交付物由 Seed 合同和 Source 能力共同约束。

系统对应做了三件事

  1. 让每个承载答案的关键主张可追溯。数字、规则、范围、例外和方法都要落到 worker-visible Source；事实保存字符坐标与哈希，可以从冻结正文重新切片核验。
  2. 把工作流和具体题分开。同一 Seed 可以在新 Source 上稳定复用，也可以在事实支持下做 1–4 个可重放修改；没有合适 Seed 时还能走 source-native，而不是硬套模板。
  3. 审核最终训练对话，而不是内部自证。Auditor 只判断训练时模型真正看到的 messages。内部 JSON 即使有证据，只要没有进入可见附件，也不能替训练样本补洞。

T先看懂八条技术不变量，再读十二个阶段

这不是十二个彼此独立的脚本，而是一条连续的数据合同。下面八条不变量决定了每一阶段为什么存在，也解释了系统为何遇到缺数据时宁可硬停。

1. 内容身份与资源身份分开

URL、resource id、card id、normalized SHA 和 document lineage 分别解决“来自哪里”“是不是同一资源”“正文是否相同”“是不是整文档的切片”等不同问题，不能只靠一个 URL 去重。

2. 证据先于题目

Generator 不能自由引用正文中的任意数字。只有先进入 key_facts、拥有 char_range 和 excerpt SHA 的事实，才能成为题目锚点。

3. 多文档是一个图问题

先建立实体、时期、版本、显式引用和语义关系边，再从图中构造 2–4 Source package；同 URL 或文本相似都不足以证明多文档必要性。

4. Seed 召回和最终选择分层

机械四轴检索负责高召回，family de-crowding 和 usage decay 控制拥挤，LLM Selector 只在固定候选池里判断 MAIN/AUX 与 exact/needs_edits。

5. Mutation 是可执行编辑脚本

modify_step/add_step/delete_step/reorder/combine 不是自然语言备注。程序重新执行 edit script 计算 canonical workflow，并检查每次编辑都有合法 fact 支撑。

6. 审核只看 worker-visible messages

先用冻结正文把 attachments、历史轮次、最终问题和 gold 物化成训练对话，再审核这份精确输入；内部元数据不能替代模型真正看到的证据。

7. SQ 与 WF 管不同对象

Sample Quality 决定题能否训练；Workflow Fidelity 决定 Seed 是否得到一次独立验证。Stable 必须两轴都过，mutated 的 WF 按角色固定为 null。

8. 所有反馈写入必须幂等

Registry 原子覆盖、checkpoint ledger、promotion pool 和 cumulative fold 都有稳定键和 before/after SHA，保证 crash/resume 或重跑不会复制题目和 Seed。

从权威资源到可重放的 Source Card

这一页只讲 Source 如何被发现、下载、冻结、抽成事实，并在去重后进入一个 100-card Unit。

主线：资源枚举 → 正文规范化与冻结 → Key Facts + Evidence Spans → 历史/lineage/内部去重 → 100-card Unit。
① 资源枚举② 冻结正文③ 事实与坐标④ 去重与 Unit

①去哪些网站,把候选页面找出来

这一节在做什么

每一批生产开始时,先去"权威站点"的索引页把候选页面枚举出来。我们不会让模型去搜索,因为那样说不清"是不是漏了几页""是不是抓了两遍同一页""昨天抓的和今天是不是同一份"。

覆盖的站点(10 类)

  • 临床/医学: clinicaltrials.gov / PubMed / OpenFDA / DailyMed / PMC
  • 政府/法律: govinfo 的 CFR & FR / USSC 量刑指南
  • 政府数据: Census ACS(本案来源)
  • 财经: SEC EDGAR XBRL / Treasury TFM / USSGL

10 类不代表每次都会均匀出现——历史去重、站点供给、API 权限都会让某些类当批为 0。

枚举结果长这样

每个候选项就是一条"任务",带一个稳定的编号: inv:<通道名>:<资源编号>。编号是稳定的,这样进程崩了也能恢复,不会"靠记忆"决定下一步要做什么。

编号会进入 manifest(之后的去重索引);不会出现的敏感字段(比如 API key)在落盘前会被替换成 REDACTED。

贯穿案例在这一节长这样

pkg_2c59b53ba2d0 由四个独立任务开始

2009 年 ACS → 任务编号 inv:census_method_data:acs/acs3/spp|data_query|2009

2010 年 ACS → 同一个通道,只有 vintage 这一个字段不同,任务编号也相应换成 |data_query|2010。

2011 和 2013 同理。四年之所以是"四份不同任务",靠的就是这个 vintage 字段把任务编号切开了。

技术实现：Collection Task 如何获得稳定身份

Input

通道 adapter、分页游标、历史 inventory，以及由数据集、查询变量、地域和 vintage 组成的 external id。

Algorithm

Adapter 机械枚举资源；driver 将 (channel_id, resource_id) 编成 inv:<channel>:<resource>，每个 task 在 state ledger 中只允许一个 terminal fate。

Output / Gate

输出可恢复的 Collection Task，而非 Source Card。分页只有 adapter 明确返回 exhausted 才算穷尽；密钥字段在持久化前统一 redaction。

不变量：枚举是确定性的资源发现，不由 LLM 决定“下一页去哪”或“哪个 URL 看起来值得抓”。这一阶段 LLM 调用数为 0。

②下载并冻结正文

为什么要"冻结"

官方页面会更新、会重定向、会下线。训练样本必须能在不重新联网的情况下 原样重放。所以一抓回来就同时存"原始字节"和"规范化后的纯文本",以规范化文本的 SHA-256 哈希作为这份正文的永久身份证。

下载完会发生什么

  1. 下到原始字节;
  2. 解析成纯文本,丢掉导航、广告、页脚;
  3. 算规范化文本的哈希,先看这个哈希以前是否见过 — 见过就跳过,绝不再花钱抽事实;
  4. 按段落切成 chunk,准备给下一步用;
  5. 写入"正文冻结仓库"。同一份正文不管被哪个任务复用,只有第一次写入的人负责,后来的人直接用。

这一步踩过的坑

会卡住的几种情形:
  • 下不动 / 超时 → 记成 "现场失败",不上算到正文;
  • 规范化文本在历史里已经存在 → 标成 "重复,跳过",不进事实抽取;
  • 同一资源遇到了两个解析器版本不同的输出 → 阻断,先对齐版本再说;
  • 写入后算出的哈希和入档前不一致 → 不允许,这次下载作废,再来一次。
贯穿案例在这一节长这样

四年 ACS 各拿到自己的正文哈希

2009 → 规范化正文哈希前缀 3784e6ec

2010 → 1f0be716

2011 → a59758ef

2013 → 263eb274

四个 hash 不同,说明四份正文确实是不同的内容;但都用了同一份 ACS 三年期 S0201 表 schema,所以 schema 事实四个 hash 都能引用。

技术实现：为什么同一正文不会重复烧事实抽取预算

身份计算

Fetch 结果先规范化，再计算 normalized_sha256。原始字节 SHA 用于下载审计，normalized SHA 才是正文内容身份。

两层缓存门

先查跨运行 HistoryIndex；再查按 parser version 隔离的 BodyCache。历史 SHA 命中会在 evidence extraction 前返回，RESUME 则交由 extraction cache 零调用恢复。

冻结写入

只有质量门通过才调用 write_frozen。写入时重新核对 SHA；同内容已有 first writer 可以复用，内容冲突则返回失败终态。

fetch bytes → normalize text → normalized SHA
           → history.sha_used?  → DUPLICATE_SKIPPED
           → BodyCache.probe    → WRITE / RESUME / FAIL_CLOSED
           → extraction cache   → 0 或 1 次 LLM
           → quality pass       → write_frozen

③抽出带原文坐标的事实

为什么不让出题 AI 自由发挥

正文往往几千字。让写题 AI 自己读、随意摘数字,会很容易"读个大概,编个细节"。所以多做一步——把正文里值得引用的句子预先抽成结构化 事实,每个事实都带两个关键东西:在原文里的字符起止位置,和这一段字符的哈希。

这个"事实"长什么样

一个事实最少包含:事实编号(如 kf_004)、事实类型(如"数值型指标")、陈述(如"夏威夷 S0201_002E 最低为 77.6")。再附加一个证据坐标:在第几段、字符 266 到 292、这段字符的哈希是什么。

这样做的好处:任何人后来怀疑"这个数字是不是编的",打开原文,把字符 266 到 292 切出来算一次哈希,应该和事实里写的哈希一致。不一致就说明事实不可信,题就不会被放行。

抽完之后还有一道自动把关

这道把关由程序跑、不花 AI:页面是否真的下下来了、是否有可引用的事实、是否像垃圾内容、主题是否真的相关。任一项不过,这张卡就直接被拒掉,不会进下一步。这是为了在流水线很早就把烂材料剔掉,不要让它们去烧后面的预算。

贯穿案例在这一节长这样

2009 年那张卡的几个关键事实

kf_000: schema = S0201_001E, S0201_002E, S0201_003E, state
kf_003: Mississippi has highest S0201_002E = 99.0
kf_004: Hawaii has lowest S0201_002E = 77.6
        → 字符 266 ~ 292
        → SHA-256 3b15b58808504b7483be8c466a243cc241b59b762b7c67f10623aeeac26bd3eb
kf_005: Hawaii has highest S0201_003E = 14.9
kf_006: Puerto Rico row is all null

其他三年的卡,各自有自己的 kf_004(数字不同),但 schema 相同。

注意:kf_006("波多黎各这行全是 null")是一个"空值事实",后面出题时它就要成为"为什么要排除这一行"的来源。

技术实现：Fact statement 为什么不能脱离 Evidence Span

Input

normalized_text 被切成带绝对字符区间的 chunks；抽取 prompt 同时收到 topic、标题和 chunk 文本。

Extraction contract

每个 key_fact.fact_id 必须在 evidence_spans 中有对应项，span 记录 chunk_id、绝对 char_range、excerpt SHA 与 covered verdict。

Quality gate

fetched_ok ∧ has_grounded_facts ∧ not_junk ∧ topic_relevant 才能进入 manifest。Inventory-first 路径以 groundedness 代替脆弱的标题词重合判断。

证据重放公式：SHA256(normalized_text[start:end]) == evidence_span.excerpt_sha256。Statement 对不对可以争论，字节是否对应不能含糊。

④去重,然后挑出本批次的 100 页

通过质量卡的页面还不能直接用

同一份官方文档可能因为切片方式不同、URL 写法不同、之前批次已经包含,产生多张看起来不一样但内容相同的卡。所以要先做"广撒网式去重",再按域配额挑出 本批次 真的要用哪些页面。

去重的几个维度

会用五个不同的"身份键"互相补足去重:卡自身的 ID、通道+资源号的组合、规范化哈希、整文档 URL、以及文档的来源链(lineage) + 在来源链里的位置。如果切片和整文档共享 URL,也不直接当一回事,会用来源链判断是不是"已存在的副本"还是"新位置上的新副本"。

每批次固定 100 页

一个批次固定 100 张卡：40 张政府、30 张临床、30 张财经。挑好后切成 4 个互不重叠的 25-卡块执行。块只是执行切片,不改变这 100 张作为一体的身份。

在 AI 开跑前的硬门槛

100 张的 JSON 都能解析、对应的正文都能加载、方案目录能读、查询预算工具和模型也都在。任一项缺失,在烧一分钱算力之前就要停下来。这就是把"先别动,确认环境齐了"写在代码里。

贯穿案例在这一节长这样

四年 ACS 卡被识别为"同组不同时段"

它们五个身份键里 channel + resource 都几乎一样,只有 vintage 不一样。系统通过实体键 + 时段键把四张归为同组,但仍然算作四个独立的 Source Card,因为正文哈希确实不同。

这四张会被分进同一个 100-卡批次的某个 25-卡块,在后面"单页题"和"多页题"两条路径都会被用到。

技术实现：四键、whole URL 与 document lineage 的执行顺序

历史去重

顺序检查 card_id、whole-document URL、(channel,rid)、normalized SHA，再让 DocumentLineageIndex 判断 duplicate 或 derived-from-existing。

本批去重

历史通过后才建立本批内部四键表；只要任何稳定键已占用，后来的卡进入 dedup ledger，不参与 domain cap。

Unit 切分

Manifest 最后才按域 cap。300 张按域排序后 round-robin 成 3×100；每个 unit 都断言 30 medical / 40 gov / 30 finance 且 card path 可解析。

关键顺序：质量门 → 历史/lineage → 本批四键 → net-new → domain cap。若先 cap 再去重，表面凑满的配额会在终验时塌掉。

⑤单页题 vs 多页题,在哪里分叉,又在哪里汇合

为什么有"单页"和"多页"两种形状

有些问题读一页文件就够了——比如"这份指南里第几条是给这种病人的"。但有些问题读一页根本不够——比如"这四年里同一群人在变少还是在变多"。前者是单页题,后者必须把多页拼起来。

单页题怎么走

一页 Source 进去,一页题目出来。附在训练对话里的页面正文上限为 16,000 字符。题目里引用的数字必须来自这一页。

多页题怎么走

2 到 4 页 Source 凑成一个包(package)。这个包的合法性要看两点:一是每页都在任务里真正被用到了(如果删掉一页答案还能出来,这一页就是凑数的);二是所有页正文合起来不超过 32,000 字符,出题才不会爆。

把多页凑在一起的依据有四类:同一件事在不同时段、同族但不同版本、文档之间互相引用、以及基于事实词的语义召回找到的相近关系。最后一种只是候选,最终能不能成包还是要看"页面是不是真的都被用上了"。

汇合点

两条路径走到写题 AI 之前看上去不同;从写题 AI 开始,就完全一样了——选方案、生成题、拼训练对话、两遍审核、入库、可能进入"晋升"流程。所以你只需要关心"输入是怎么凑的",不必关心"出题以后的事是不是同一套"。

贯穿案例在这一节长这样

pkg_2c59b53ba2d0 走的是多页路径

四年 ACS 卡被发现:共享一个实体键 census|acs/acs3/spp|geo=state:*|vars=S0201_001E,S0201_002E,S0201_003E,共享同样的 schema,有共同的对比对象(夏威夷、密西西比、波多黎各),但 period key 各不相同(2009/2010/2011/2013)。

系统标出关系是 "不同时段",而不是"凑巧长得很像的页面"。

接下来系统做"必要性检查":删掉任何一年,比如 2011,都会让"四期并列对比"变成三期,2011 的四个事实 ID 全部失去来源。所以这个包通过必要性检查——4 个来源都必要。

技术实现：关系图怎样变成一个真正必要的 Source Package

Relation index

机械身份边包括 same entity、different period、same family、different version；另有显式引用边和语义召回边。边保存证据与分数，不直接等于 package。

Thick + comparability

成员先过正文长度、facts 数、spans 数和 body source 门，再要求同一 instrument、共享稀有 metric tokens；“同实体 + 不同日期”只用于召回，不能独自成包。

Package score

0.5×structural + 0.3×evidence_alignment + 0.2×source_necessity。正文越长不会加分；每个成员缺失会破坏哪个时期/规则必须写进 removal_breaks。

多文档合同：2–4 Sources、总正文 ≤32K、每源至少贡献 operation-relevant facts、删除任一成员会使任务定义不完整。

⑥选一个"工作方案"

什么是"工作方案"

系统维护着一份"过去哪些做法被验证过可以出题"的方案库。一个方案不是一个答案模板,而是一套可执行的步骤,比如:

  1. 定义可比指标、单位和比较期间;
  2. 取得每一对象的该指标;
  3. 用同一套口径对齐;
  4. 输出并列对比表并解释。

方案从哪来

两类:已沉淀方案(当前目录 221 条)和运行时方案(历史上别批题出得好,系统回头把它们抽象成新方案)。后者有两种持久状态：等待跨卡验证的 candidate，以及已经被不同卡原样复用且审核全过的 active。pending 只存在于 checkpoint 前的候选队列，不属于 cumulative master 状态。

怎么挑方案

对当前这一页或这个包,系统把每个方案都投射到四个维度上打分:内容是否对得上、操作类型是否对得上、证据形状是否对得上、最后输出物是否对得上。按这几个维度的加权融合给出一个排序,挑一个"主方案",再选 0 到 2 个"辅助方案"补充灵感,但不能因此模糊主方案该做的事。

挑不到方案怎么办

三种合法处理:(一)允许"原生出题",不假装在复用方案,从这一页本身真的能出一道好题;(二)返回"诚实零题",意思就是这一页今天不要勉强出题;(三)修一修再加进来,就是下一节要做的事。这三件事都不是程序崩了——它们都是合法的"今天的结论"。

技术实现：四轴召回、族去拥挤和 Selector 分别负责什么

统一画像

Static catalog 和 runtime registry 先投影成同一个 SeedRetrievalProfile。origin 只留作审计，不参与排序；排序只读内容、证据、操作和交付物四个轴。

机械召回

四轴分别做 BM25/RRF。一个 Seed 即使四轴都命中，也只累计最强的两轴贡献，避免字段写得多就天然占优。随后按直接父种子 family 做贪心去拥挤，每族最多 3 席。

H 没有消失：当前 usage_decay_half_life=4，它在 family 定员之后按本批使用次数重排候选。

LLM Selector

Selector 只能在固定候选池内选择：恰好一个 MAIN，判断 exact 或 needs_edits，再选最多两个 AUX。它没有权限把池外 seed 临时塞回来。

池构造顺序：family 定员到 30 → usage decay 只重排、不逐出 → raw-relevance floor 保留至少 2 席。这个顺序同时控制热门方案垄断与冷门方案误入。
H=4 到底做什么：adjusted_score = relevance × 2^(-usage_count / 4)。同一 Seed 在本批使用 0 次保留 100% 分数，4 次降到 50%，8 次降到 25%。usage_count 只计当前批次，Seed 一旦被选中并送入 Generator 就立即 +1，不等题目最终成功；resume 会恢复本批计数，跨批累计采用次数不参与衰减。H 只改变 30 个既定候选的展示顺序，不改变成员集合；raw floor 仍保护最相关的 2 个候选。

⑦把题具体写出来

这一步是谁在做

大模型根据方案 + 一页或多页源材料 + 已经抽好的事实,写出三样东西:问题是什么(gold answer)、答案是怎么一步步想出来的(reasoning)、以及引用了哪几个事实。

三种"出题姿势"

三种姿势对应三种不一样的工作量:

  • 直接复用(stable):方案完全适用,工作步骤原封不动。这是验证"方案跨页是否成立"的最好证据。
  • 方案微调(mutated):方案整体合适,但要改 1 到 4 处。每处修改都要有事实依据(改了哪句话、有哪个事实支持这么改)。
  • 原生题(source-native):没有现成方案能套,但这一页本身能撑起一道好题。不会被算成"复用了方案"。

被卡住的几种情形

不会放过这道题的情况:
  • 题目记录不是合法 JSON;
  • 引用的某个事实,在源材料里查不到;
  • 修改超过 4 处,或者某处修改没事实依据。

这些都算"这一页今天出不了这道题",不是工程事故。

技术实现：不是“写一段题”，而是构造并验证 TaskSignature

结构化输出

Generator 必须输出完整 TaskSignature：task id、source ids、role、问题、gold answer、reasoning、used facts、work steps、source-use map 和拒绝原因。JSON 只是语法门，字段间关系才是语义门。

可重放修改

stable 不允许实质编辑；mutated 必须给 1–4 个 modify_step。程序从 seed 原步骤机械应用这些 edits，结果必须逐项等于 final_work_steps。

事实闭包

多文档事实先命名空间化为 source_card_id::fact_id。每个 used fact、每个 edit 的 supporting facts、每个 source-use 声明都必须落在 Package 提供的合法事实集合内。

合法 honest zero：模型可以说材料不足，但必须使用允许的拒绝码，并由机械 feasibility gate 复核；如果机械门认为可做，系统只允许一次 bounded repair，不能无限追问模型。

⑧把题拼成"训练对话"

为什么要先拼再审

审核这一步必须和训练时模型看到的一模一样。如果审核看的是别的版面的文本,那审核通过也不能保证训练时模型真的能答对。所以我们先把题目物化成训练时模型看到的那份材料,这份材料带一个哈希,然后审核看的就是它。

多页题长这样

系统消息写"请根据提供的资料回答"。然后附件按页面一段一段贴,每页一段,带"这是第 N 段、共 M 段、来源是 X、证据锚点是这几个事实"。最后用户的提问出现,再后面跟着标准答案。

关键的顺序硬要求

整段对话必须以"最后一句是用户提问,再后面一句是标准答案"结尾。把整个对话序列化后算一个哈希,这就是"训练样本的身份证"。

技术实现：先按事实选窗口，再生成模型最终会看到的 messages

事实驱动窗口

每个 namespaced fact 先回到对应 source 的 evidence span，再围绕 span 扩展上下文。一个 source 有多个事实时合并重叠窗口，不能只截第一条事实附近的文本。

多源预算

Package 给每个成员至少 4K 字符基础份额，再按 source importance 与 facts 密度分配余量；最终所有窗口总和仍受 32K 上限约束。任一必要 source 没窗口就拒绝，而不是静默少贴一页。

精确物化

最终记录固定为 system → user(attachments + question) → assistant(gold answer)。Auditor 后续读取这三个 message，而不是重新从 Source Card 拼一个“差不多”的视图。

训练身份证：training_sample_sha256 = SHA256(canonical_json(messages + attachments metadata))。同一题若可见窗口或消息顺序变化，就是另一份训练样本。

⑨两遍审核——题好不好,有没有照方案做

为什么是"两遍",而不是一遍

审核其实问了两个不同的问题:

  • 审核题面(Sample Quality):这道训练样本好不好?对话里的人能不能从给定的正文里找到证据答对?答案本身是否正确?
  • 审核方案(Workflow Fidelity):这道题是不是真的执行了它声称在用的那个方案?

前一关决定 题能不能进题库;后一关决定 方案能否被验证 / 被晋升。两个问题不同,管的事不同,所以分开问。

三种姿势的审核规则不一样

  • 直接复用的题:两关都要过——题要好,而且必须真的执行了方案。
  • 方案微调或原生题的题:只问前一关。问"是否执行了方案"不公平,因为本来就没打算执行——这种题的"方案那一栏"在出生时就程序写成了空,这是设计,不是失败。

这个区别很重要:后面晋升方案要靠"另一批次的题用这个方案原封不动地答对了一次",所以错把改过的题算成"执行了方案"会污染晋升证据。

审核前会给 AI 看一堆程序跑出来的诊断

比如:哪个事实真正去原文比对过、哪几步有证据、哪几步落空、整道题的"可行性比例"。这些数字本身不裁决——裁决由另一次 AI 看诊断后给出。如果 AI 那边出问题(超时、JSON 解析错),这道题就要标为"基础设施未完成",不能悄悄放过去。

技术实现：SQ 与 WF 是两条不同的 release 轴

机械诊断

先计算所有 used facts 是否可见、source 使用是否闭合、答案数字是否能在 worker-visible attachments 找到、work steps 是否可重放。诊断随精确 messages 一起交给 focused auditor。

角色域

stable 的 WF 必须得到 True；mutated 与 source_native 的 WF 强制为 null，防止“改过方案”伪装成“原样验证方案”。

放行真值表

stable：SQ pass ∧ WF True；mutated/source-native：SQ pass 即可，WF 必须为 null。显式审计失败写入 rejected；审计调用或解析失败写 infra 状态，不得放行。

为什么不统一要求 WF：WF 衡量“有没有原样执行 seed”，不是“题好不好”。对 mutated 强求 WF=True 会把产品定义上互斥的两件事混成一个分数。

⑩先隔离入库，再统一导出

题库里有几样东西

审核过的题不会统统混在一起。每批次有自己的隔离目录:合格题、待复审题、被拒题、本批次新发现的"待审方案"、本批次产生的方案,以及各种账本。

旧训练样本和新题现在是什么关系

生产时仍然隔离：旧流水线与每个 M7/M8 unit 各写各的 registry。提交前的统一导出已经完成：它先校验 question/training 配对，再用训练内容哈希生成新的 sample_id，所以同名但内容不同的题可以保留，内容完全相同的记录只留一份。当前统一集合共有 3,069 条通过审计的样本。

技术实现：Registry 原子写与统一导出的两种身份

Unit registry

categorize() 把题分 clean、review、rejected；题和 training sample 成对写入。bucket 写入先锁目录，再写临时文件并 os.replace，避免中途断电留下半行 JSON。

生产 task id

多文档在首次落盘前加 __pkg<12-hex>，用于区分同一 anchor 的单文档题与不同 package 题。但 task id 仍是生产追踪键，不再被当作训练内容的唯一身份。

统一 sample id

Exporter 对规范化 messages 与关键 metadata 计算内容哈希，生成 sft4b_current_<content-hash>。同 task id、不同内容进入 collision ledger 并同时保留；同内容才去重。

一致性门：每个训练样本必须能找到对应 question、message roles 合法、assistant 非空、metadata 可追溯到 registry。富审计 JSON 不直接喂模型，最终记录只保留一个完整的 messages 数组。

⑪让那些"改过的方案"将来有机会被重用——晋升与回收

为什么不立刻把新方案入库

抽象方案、决定"这算不算一个新方案"、验证"它在另一张卡上是不是也能用"——这些都要花钱。如果让主流程在每道题结束时顺手做,预算不可控,resumability 也乱。所以这步被推迟到了另外一个独立预算的工序里去做。

这道推迟的工序做什么

  1. 读出所有"待审方案"(pending);
  2. 先做程序级检查:是不是合法 JSON、有没有和已有方案重复、是不是能由修改操作重放;
  3. 再问一次 AI:这是一个"新且有用的工作方式"吗;
  4. 如果是,接收为"候选方案",记到账本,这批次的方案文件多一行;
  5. 如果是,这批次结束后,会和累计的大方案表做一次"原子合并"。

什么时候算"晋升"

"候选方案"还不够。要等另一张不同的卡也用了这个方案、原封不动地出了一道合格题、并且那道题的"是否执行了方案"也为真——这样才算"方案被独立复用了一次",才能从候选升成"已晋升方案"。"已晋升"意味着这个方案在不同的素材上独立工作过,可以说"它不再只是这一次的事件"。

这一步偶尔被错误地简化成"题通过了 = 方案已晋升"。不要这样理解——同一张卡上的自我复用不算验证。

合并是怎么个合并法

每次合并四种状态变化之一:新加一条、把某条从"候选"翻成"已晋升"、给某条追加"已验证过的卡"、或者什么都不变(目标已经包含同样的状态)。合并会记下合并前后的快照哈希,确保同一批数据再跑一次也不会产生任何新的变化——这套机制是为了支持"任意重跑不乱"。

贯穿案例在这一节长这样

pkg_2c59b53ba2d0 现在停在什么阶段

它产出的"改过的方案"现在以 pending 状态躺在 pending_candidates.jsonl:53。还没变成"候选方案"——要等独立预算的那个工序下次开起来才会处理它。

它也还不能说自己"已晋升"——这是必然的,因为这是一道新题,还没有"另一张不同卡 + 原封不动"地复用这个方案的记录出现。我们之后会在别的批次上验证它,但那不是这批的事。

技术实现：主流程零额外调用，Checkpoint 与 Fold 独立闭环

Deferral

主流程只把合格 mutated signature 写成 pending record，不在 finalize_run 内隐式调用抽象器。这样主任务的结束时点和预算可预测。

Checkpoint

每个 25-card chunk 后，独立 worker 读取尚未处理的 pending：先做 schema、实体泄露、悬空 fact、work-step replay 与近重复机械门，再在剩余共享预算内做 novelty、抽象与验证。

Promotion + Fold

Promotion 只扫描完整 runtime pool；不同 card 的 stable 题且 SQ/WF 都过，才追加 validated card 或把 candidate 翻成 active。Fold 用文件锁把 append/flip/extend/noop 合并进 cumulative master。

幂等键与硬报警：pending/checkpoint 以 (seed_id, task_id) 去重；引用了 runtime seed 但 promotion pool 找不到时抛错。静态 slot_/sc_/kf_ seed 不参与这个 runtime 完整性断言。

⑫失败的样子、预算纪律,以及今天的数字

四种"不成功",不要互相顶替

这一套流程里有四种"今天没出题"的情形,长得不一样,处理方式也不一样。

  • 没合适方案:当前素材不适合任何已有方案,又不值得从素材本身出一道原生题。诚实零题,今天就到这里。
  • 质量拒绝:模型写错了,或证据挂不住。可以重试一两次(同预算内),再不行就拒绝。
  • 基础设施失败:网络抖动、429 限速、响应截断、JSON 解析错。可以视情况重试,但需要操作员显式授权,不能自动化。
  • 契约 bug:正文丢了、账本路径错了、指纹漂了。先硬停,一分钱都不让花在 AI 上;回到代码里修,改完跑一次 fake E2E。

预算是一条合同

一个批次从头到尾只用一个共享预算,设硬上限。多页出题、单页选择器、出题、审核、方案抽象、JSON 修补都吃这同一个上限。预算用完,本批自然收口。任何子环节不允许偷偷建自己的 AI 客户端绕过这条线。

重跑也不能乱的"指纹"

下一次开跑前,系统先比对上次跑时的所有输入快照(本批次选了哪些卡、当前方案目录长啥样、提示词模板长啥样、正文仓库是否有变)。如果其中任一项漂了,系统会拒绝恢复,要求显式确认;如果没漂,可以放心接上次的进度。

贯穿案例在这一节长这样

pkg_2c59b53ba2d0 的小插曲

这题在 unit_4 第一次跑的时候,出题那一步撞上了一次 MiniMax 429——属于"基础设施失败"。在操作员授权后重试,这次跑通了。

这件事没有改变源材料、改方案、改题目,也没有把"质量被拒"的题偷偷放过去——它只是一次网络抖动的代价,需要操作员显式批准。

技术实现：一个 Unit 只有一个输入身份、一个预算和一个硬停出口

Preflight

先验证 100-card manifest、30/40/30 域配额、card JSON、body cache、seed master、client owner 与 API key。Gate 失败写明确原因并退出，promotion 与 fold 均不运行。

Chunk contract

完整 100-card manifest 构成 run-level fingerprint；四个 25-card --only 只是互不重叠的执行切片。四块 union 必须恰好等于 unit，任何 card 只能出现一次。

SharedBudget

多文档、四个单文档 chunk、Selector、Generator、Auditor、JSON repair 和 Checkpoint 共享计数器。当前实现先为多文档预留不超过 100 calls，再把剩余预算交给单文档与 checkpoint。

恢复指纹：manifest、static/runtime seeds、prompts、config、blueprints、模块代码与 body cache 都入 fingerprint。run 内自己写入的 seeds 只能通过 append ledger + 时间锚重放掉；无法解释的 drift 一律拒绝 resume。
